**Status:** done

## Goal
The desktop / mobile apps can list, update and sign out their installs, open deep-linked
invitations and accept them, and create a first workspace. The web Profile page shows the app
installs and can sign any of them out.

## Approach
- **Devices** (`App\Http\Controllers\AppApi\DeviceController`, `DeviceResource`):
  - `GET /api/v1/devices` — the user's active devices, most recently used first, `current: true`
    for the calling device. Never token hashes or the push token (only `has_push_token`).
  - `PATCH /api/v1/devices/current` (`UpdateDeviceRequest`) — name / app_version / os_version /
    push_token (encrypted cast on the model). The card said `POST /devices`; the row already
    exists after the sign-in exchange, so it is an update of the calling device.
  - `DELETE /api/v1/devices/{device}` — own active device only, else 404; `AppTokens::revoke`
    (`sign_out` for the calling device, `user` for another one) → 204.
- **Web**: `DELETE /profile/app-devices/{device}` (`AppDeviceController`, session + CSRF, own
  devices only → 404) revokes with reason `user`. `ProfileController::edit` passes `appDevices`
  (same `DeviceResource`). `Profile/Partials/AppDevices.tsx` in the Notifications card under the
  browser push devices: icon per platform, name, app version, last used, signed in, "Sign out".
  e2e-only `POST /profile/app-devices/e2e-create` (APP_ENV=e2e) seeds a device + token for the spec.
- **Invitations** (`AppApi\InvitationController`, same rules as the web one):
  - Shared rules move onto the model: `WorkspaceInvitation::emailMatches()` and `acceptBy()`
    (limit gate → mark accepted → add unless already a member → notify), used by the web
    `InvitationController::accept`, `acceptPendingForUser` and the API.
  - `GET /api/v1/invitations/{token}` — workspace, inviter, email, role, expires_at, expired,
    accepted, email_matches, already_member; unknown → 404.
  - `POST /api/v1/invitations/{token}/accept` (`verified`) — 404 unknown, 410 expired, 403 other
    email, 402 `limit_reached`; already accepted / already member → 200 with the workspace when
    the user is in it, else 409. Returns `{workspace: {id, slug, name, role}}`.
- **Workspaces**: `POST /api/v1/workspaces` (`verified`) — the web store's rules move into
  `App\Http\Requests\StoreWorkspaceRequest` + `Workspace::createOwnedBy()` (limit gate, create,
  owner as admin), used by both. 201 `{workspace}`.
- **Limits in /api/v1**: `LimitReached::render` answers api/v1 requests in the App API shape
  (`AppApiErrors::limitReached`: 402 `{message, code: "limit_reached", limit: {...}}`).

## Notes
- Responses use the `{data: …}` envelope (lead's convention); DELETE → 204.
- `Tests\Feature\AppApi\Concerns\ForgetsGuardsBetweenRequests`: in tests the `app` request guard
  keeps the user it resolved across requests, so a revoked token would still pass. App API tests
  that make several requests use it (not with `actingAs`).
